Vulkan Descriptor Pool System - Design Specification
Goals

Implement a scalable Vulkan descriptor allocation system supporting:

Static/Persistent descriptor pools
Long-lived descriptor sets
Dynamic pool growth
Optional individual descriptor freeing
Dynamic/Transient descriptor pools
Per-frame temporary descriptor sets
Fast allocation
Whole-pool reset
No individual freeing

System must:

scale automatically
avoid fragmentation where possible
support future bindless migration
minimize Vulkan allocation overhead
High-Level Architecture
DescriptorAllocatorPersistent
    ├── currentPool
    ├── usedPools
    └── freePools

DescriptorAllocatorFrame[FramesInFlight]
    ├── framePool
    └── vkResetDescriptorPool() every frame
1. Persistent Descriptor Allocator
Purpose

Used for descriptor sets with arbitrary or long lifetimes.

Examples:

material descriptor sets
texture bindings
static compute resources
renderer-global resources
editor/UI descriptors
Vulkan Pool Flags

Pools use:

VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT

to allow:

vkFreeDescriptorSets(...)
Behavior
Allocation
Allocate from currentPool
On exhaustion:
create new VkDescriptorPool
switch current pool
retry allocation
Freeing

Supports:

individual descriptor freeing
optional delayed destruction if needed
Pool Lifetime

Pools remain alive until:

renderer shutdown
allocator destruction
explicit pool garbage collection
Internal Structure
class DescriptorAllocatorPersistent
{
    VkDevice device;

    VkDescriptorPool currentPool;

    std::vector<VkDescriptorPool> usedPools;
    std::vector<VkDescriptorPool> freePools;

public:
    VkDescriptorSet Allocate(...);
    void Free(VkDescriptorSet set);
    void Reset();
};
Pool Exhaustion Handling

On allocation failure:

VK_ERROR_OUT_OF_POOL_MEMORY
VK_ERROR_FRAGMENTED_POOL

allocator:

grabs/reuses free pool OR creates new pool
retries allocation
Pool Sizing

Pools are intentionally large.

Example:

VkDescriptorPoolSize poolSizes[] =
{
    { VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,         1024 },
    { VK_DESCRIPTOR_TYPE_STORAGE_BUFFER,         1024 },
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,2048 },
    { VK_DESCRIPTOR_TYPE_STORAGE_IMAGE,           256 },
};

maxSets = 4096;
2. Dynamic/Transient Descriptor Allocator
Purpose

Used for short-lived descriptor sets.

Examples:

per-frame descriptors
temporary compute descriptors
transient material instances
temporary render graph resources
Vulkan Pool Flags

Pools use:

flags = 0

NOT:

VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT

because:

individual freeing is unnecessary
reset model is faster
avoids fragmentation
Behavior
Allocation
allocate freely during frame
Reset

At beginning/end of frame:

vkResetDescriptorPool(...)

This invalidates all descriptor sets allocated from the pool.

Structure

One allocator per frame-in-flight:

DescriptorAllocatorFrame frames[FramesInFlight];

Each contains:

class DescriptorAllocatorFrame
{
    VkDescriptorPool pool;

public:
    void Reset();
    VkDescriptorSet Allocate(...);
};
Frame Lifecycle
Frame Begin
    -> reset descriptor pool

Rendering
    -> allocate transient descriptor sets

Frame End
    -> descriptor sets become obsolete automatically
Descriptor Pool Creation Strategy
CreatePool()

Allocator creates pools using configurable ratios.

Example:

struct PoolSizeRatio
{
    VkDescriptorType type;
    float ratio;
};

Example ratios:

{
    { VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,          2.0f },
    { VK_DESCRIPTOR_TYPE_STORAGE_BUFFER,          2.0f },
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER, 4.0f },
    { VK_DESCRIPTOR_TYPE_STORAGE_IMAGE,           1.0f },
}

Pool sizes derived from:

descriptorCount = ratio * maxSets;
Allocation API
Allocate()
VkDescriptorSet Allocate(
    VkDescriptorSetLayout layout);

Optional extension:

VkDescriptorSet Allocate(
    VkDescriptorSetLayout layout,
    void* pNext);
Pool Recycling
Persistent Allocator

Supports:

recycling unused pools
future defragmentation strategies

Optional:

move fully unused pools into freePools
Dynamic Allocator

No recycling needed.

Pool survives permanently and resets each frame.

Threading Considerations
Vulkan Requirement

Descriptor pool allocation is NOT thread-safe.

Recommended Strategy

Either:

mutex around allocation
OR:
one allocator per thread

Preferred future design:

ThreadLocalDescriptorAllocator

especially for transient descriptors.

Descriptor Set Layout Policy
Important

Descriptor set layouts should be:

cached
reused aggressively
immutable after creation

Avoid recreating layouts frequently.

Error Handling

Allocation must detect:

VK_ERROR_OUT_OF_POOL_MEMORY
VK_ERROR_FRAGMENTED_POOL

and recover automatically.

Any other error:

treated as fatal Vulkan error
Future Bindless Compatibility

System should remain compatible with future:

descriptor indexing
bindless textures
bindless buffers

Expected future direction:

fewer descriptor set allocations
large persistent descriptor arrays
descriptor updates instead of allocation churn

Current allocator design should therefore:

remain modular
not assume heavy descriptor allocation forever
Recommended Engine Usage
Persistent Allocator

Use for:

materials
textures
renderer-global descriptor sets
static compute resources
Dynamic Allocator

Use for:

per-frame descriptors
temporary GPU jobs
render graph transient resources
dynamic object bindings
Non-Goals

This system currently does NOT include:

descriptor set layout reflection cache
bindless implementation
descriptor update templates
descriptor buffer extension
multithreaded descriptor allocation
automatic pool shrinking

These may be added later.

Final Design Summary
Persistent Allocator
Feature	Supported
Dynamic pool growth	Yes
Individual descriptor free	Yes
Pool reset	Optional
Fragmentation possible	Yes
Long-lived descriptors	Yes
Dynamic Allocator
Feature	Supported
Dynamic pool growth	Optional
Individual descriptor free	No
Pool reset	Every frame
Fragmentation resistant	Yes
Long-lived descriptors	No





















Your outline is directionally correct, but I would reorder it slightly. The material and G-buffer contracts need to exist before the pipelines and draw-call routing can be designed cleanly.
Recommended order
1. Define the deferred contract
Before implementation, lock down:
- MaterialPass::deferred
- A DeferredRenderState
- Which materials remain forward-only:
  - transparent
  - skybox
  - probably wireframe
- Exact G-buffer channel meanings
- Normal coordinate space
- Depth-based world-position reconstruction
- How receiveShadows is encoded per pixel
A reasonable initial G-buffer contract would be:
Texture	Channels
Albedo SRGB	RGB = base color, A = available
Normal A2B10G10R10	RGB = encoded world-space normal, A2 = flags or unused
Material RGBA8	R = metallic, G = roughness, B = ambient occlusion, A = flags
Depth D32	hardware depth


The flags must account for things such as receiveShadows and potentially unlit materials. Emissive HDR cannot be represented properly by this contract, so either explicitly defer emissive support or add another buffer later.
2. Add deferred material support
This should precede draw calls because the draw-call implementation needs a valid deferred material and pipeline lookup.
Likely additions:
- MaterialPass::deferred
- DeferredRenderState
- DeferredMaterial in core
- Deferred factories through:
  - IRenderer
  - core Renderer
  - MaterialManager
  - MaterialShaderManager
  - Vulkan Material
  - Vulkan MaterialShader
- RenderStageTraits<RenderStage::deferredGeometry>
I recommend a distinct deferred material type for now. Refactoring a material into a Unity-like multi-pass material containing deferred, forward, shadow, and fallback passes is a much larger architectural step.
3. Add the deferred geometry pipeline
This is the per-material pipeline. It should have:
- Three color blend attachment states, all with blending disabled
- Depth test and depth writes enabled
- One sample
- Dynamic viewport, scissor, and cull mode
- The deferred geometry render pass
- Pipeline variants for each vertex memory layout
The geometry shader interface and pipeline should be developed together because shader reflection determines vertex inputs, descriptors, and pipeline layout.
4. Add deferred draw-call storage and routing
Add:
std::vector<DeferredDrawCall> m_deferredDrawCalls;
std::vector<DeferredDrawCall*> m_sortedDeferredDrawCallPointers;
DeferredDrawCall will be very similar to ForwardDrawCall.
The existing Renderer::DrawMesh() API can route based on MaterialPass:
deferred material → deferred geometry list
forward material  → forward list
No separate public DrawDeferredMesh() API should be necessary.
Remember to integrate deferred calls into:
- descriptor-binding checkout/return
- model-data updates
- shader-data updates
- pending-use tracking
- frame reset
- sorting
Deferred geometry is opaque, so sorting should favor pipeline/material grouping and optionally front-to-back depth. It does not need transparent back-to-front sorting.
5. Record deferred geometry draws
Populate the existing empty geometry render-pass block with logic equivalent to forward recording:
- Pipeline changes
- Pipeline-layout changes
- Static descriptor sets
- Per-shader descriptor sets
- Per-draw descriptor sets
- Push constants
- Vertex/index buffers
- Indexed draws
The render pass itself should continue to execute even when the deferred draw list is empty so the G-buffers and depth are always cleared.
6. Add deferred lighting as a renderer-owned fullscreen operation
Deferred lighting should not use DeferredDrawCall or the sorted geometry list. It is one fullscreen draw per frame.
I would model it similarly to presentation:
- Dedicated DeferredLightingPipeline
- Renderer/default-resource-owned lighting shader/material
- No depth attachment
- Depth testing disabled
- No blending
- One fullscreen triangle, preferably generated from SV_VertexID
- G-buffer and depth textures bound per frame
- Static scene/light/shadow descriptor sets bound normally
The lighting draw should always execute, even when there are no geometry calls. Empty depth/G-buffers should simply produce the cleared background color.
7. Write shaders incrementally
I would not write the entire lighting model in one pass:
1. Geometry shader writes the defined G-buffer contract.
2. Lighting shader displays albedo only.
3. Reconstruct world position from depth.
4. Decode and visualize normals.
5. Add one directional light.
6. Add positional lights.
7. Add shadow sampling.
8. Add material parameters and flags.
Important details:
- Sampling the SRGB albedo texture automatically converts it to linear space.
- Lighting writes linear color to R16G16B16A16_SFLOAT.
- Existing post-processing applies gamma correction later.
- Use Texture2D.Load() for G-buffer/depth access to avoid filtering packed material data, normals, and depth.
8. Test the mixed pipeline
The meaningful final test is not merely a deferred object. Test:
- Deferred opaque object
- Forward transparent object over it
- Forward skybox/background
- Correct depth interaction between deferred and forward
- Multiple frames in flight
- Shadowed and non-shadow-receiving objects
- Resize/recreation
- Vulkan validation layers
The most important adjustment to your plan is therefore: add material/G-buffer contracts before draw calls, and treat deferred lighting as one global fullscreen operation—not as part of each deferred draw call.

Vulkan Descriptor Pool System - Design Specification
Goals

Implement a scalable Vulkan descriptor allocation system supporting:

Static/Persistent descriptor pools
Long-lived descriptor sets
Dynamic pool growth
Optional individual descriptor freeing
Dynamic/Transient descriptor pools
Per-frame temporary descriptor sets
Fast allocation
Whole-pool reset
No individual freeing

System must:

scale automatically
avoid fragmentation where possible
support future bindless migration
minimize Vulkan allocation overhead
High-Level Architecture
DescriptorAllocatorPersistent
    ├── currentPool
    ├── usedPools
    └── freePools

DescriptorAllocatorFrame[FramesInFlight]
    ├── framePool
    └── vkResetDescriptorPool() every frame
1. Persistent Descriptor Allocator
Purpose

Used for descriptor sets with arbitrary or long lifetimes.

Examples:

material descriptor sets
texture bindings
static compute resources
renderer-global resources
editor/UI descriptors
Vulkan Pool Flags

Pools use:

VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT

to allow:

vkFreeDescriptorSets(...)
Behavior
Allocation
Allocate from currentPool
On exhaustion:
create new VkDescriptorPool
switch current pool
retry allocation
Freeing

Supports:

individual descriptor freeing
optional delayed destruction if needed
Pool Lifetime

Pools remain alive until:

renderer shutdown
allocator destruction
explicit pool garbage collection
Internal Structure
class DescriptorAllocatorPersistent
{
    VkDevice device;

    VkDescriptorPool currentPool;

    std::vector<VkDescriptorPool> usedPools;
    std::vector<VkDescriptorPool> freePools;

public:
    VkDescriptorSet Allocate(...);
    void Free(VkDescriptorSet set);
    void Reset();
};
Pool Exhaustion Handling

On allocation failure:

VK_ERROR_OUT_OF_POOL_MEMORY
VK_ERROR_FRAGMENTED_POOL

allocator:

grabs/reuses free pool OR creates new pool
retries allocation
Pool Sizing

Pools are intentionally large.

Example:

VkDescriptorPoolSize poolSizes[] =
{
    { VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,         1024 },
    { VK_DESCRIPTOR_TYPE_STORAGE_BUFFER,         1024 },
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,2048 },
    { VK_DESCRIPTOR_TYPE_STORAGE_IMAGE,           256 },
};

maxSets = 4096;
2. Dynamic/Transient Descriptor Allocator
Purpose

Used for short-lived descriptor sets.

Examples:

per-frame descriptors
temporary compute descriptors
transient material instances
temporary render graph resources
Vulkan Pool Flags

Pools use:

flags = 0

NOT:

VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT

because:

individual freeing is unnecessary
reset model is faster
avoids fragmentation
Behavior
Allocation
allocate freely during frame
Reset

At beginning/end of frame:

vkResetDescriptorPool(...)

This invalidates all descriptor sets allocated from the pool.

Structure

One allocator per frame-in-flight:

DescriptorAllocatorFrame frames[FramesInFlight];

Each contains:

class DescriptorAllocatorFrame
{
    VkDescriptorPool pool;

public:
    void Reset();
    VkDescriptorSet Allocate(...);
};
Frame Lifecycle
Frame Begin
    -> reset descriptor pool

Rendering
    -> allocate transient descriptor sets

Frame End
    -> descriptor sets become obsolete automatically
Descriptor Pool Creation Strategy
CreatePool()

Allocator creates pools using configurable ratios.

Example:

struct PoolSizeRatio
{
    VkDescriptorType type;
    float ratio;
};

Example ratios:

{
    { VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,          2.0f },
    { VK_DESCRIPTOR_TYPE_STORAGE_BUFFER,          2.0f },
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER, 4.0f },
    { VK_DESCRIPTOR_TYPE_STORAGE_IMAGE,           1.0f },
}

Pool sizes derived from:

descriptorCount = ratio * maxSets;
Allocation API
Allocate()
VkDescriptorSet Allocate(
    VkDescriptorSetLayout layout);

Optional extension:

VkDescriptorSet Allocate(
    VkDescriptorSetLayout layout,
    void* pNext);
Pool Recycling
Persistent Allocator

Supports:

recycling unused pools
future defragmentation strategies

Optional:

move fully unused pools into freePools
Dynamic Allocator

No recycling needed.

Pool survives permanently and resets each frame.

Threading Considerations
Vulkan Requirement

Descriptor pool allocation is NOT thread-safe.

Recommended Strategy

Either:

mutex around allocation
OR:
one allocator per thread

Preferred future design:

ThreadLocalDescriptorAllocator

especially for transient descriptors.

Descriptor Set Layout Policy
Important

Descriptor set layouts should be:

cached
reused aggressively
immutable after creation

Avoid recreating layouts frequently.

Error Handling

Allocation must detect:

VK_ERROR_OUT_OF_POOL_MEMORY
VK_ERROR_FRAGMENTED_POOL

and recover automatically.

Any other error:

treated as fatal Vulkan error
Future Bindless Compatibility

System should remain compatible with future:

descriptor indexing
bindless textures
bindless buffers

Expected future direction:

fewer descriptor set allocations
large persistent descriptor arrays
descriptor updates instead of allocation churn

Current allocator design should therefore:

remain modular
not assume heavy descriptor allocation forever
Recommended Engine Usage
Persistent Allocator

Use for:

materials
textures
renderer-global descriptor sets
static compute resources
Dynamic Allocator

Use for:

per-frame descriptors
temporary GPU jobs
render graph transient resources
dynamic object bindings
Non-Goals

This system currently does NOT include:

descriptor set layout reflection cache
bindless implementation
descriptor update templates
descriptor buffer extension
multithreaded descriptor allocation
automatic pool shrinking

These may be added later.

Final Design Summary
Persistent Allocator
Feature	Supported
Dynamic pool growth	Yes
Individual descriptor free	Yes
Pool reset	Optional
Fragmentation possible	Yes
Long-lived descriptors	Yes
Dynamic Allocator
Feature	Supported
Dynamic pool growth	Optional
Individual descriptor free	No
Pool reset	Every frame
Fragmentation resistant	Yes
Long-lived descriptors	No




















Question:
My renderer now supports forward and deferred materials.
How would a workflow for my fluid dynamics project look like if i want to add realistic fluid rendering to it?
So i want to replace the current volumeRaycast shader with something that can reconstruct the fluid surface and use it to reflect and refract rays on it.







Answer:
Worked for 4m 51s
I would keep the fluid out of the deferred G-buffer. The best fit for Ember is:
SPH simulation
    ↓
3D density field
    ↓
Implicit-surface reconstruction
    ↓
Refractive forward/composite pass
    ↓
Remaining transparent objects
    ↓
Post-processing
You already have the expensive first half: [`densityTexture3d.comp.hlsl`](/home/tom/Documents/Ember/projects/fluidDynamics/shaders/src/densityTexture3d.comp.hlsl) converts the particles into a scalar density field, and [`volumeRaycast.frag.hlsl`](/home/tom/Documents/Ember/projects/fluidDynamics/shaders/src/volumeRaycast.frag.hlsl) already performs the required ray-box traversal.
1. Reconstruct an implicit surface
Treat the fluid as the iso-surface
density(position) = targetDensity × surfaceRatio
A surfaceRatio around 0.4–0.6 is a reasonable starting range, but it should remain editable.
Replace the volume integration loop with:
1. Intersect the camera ray with the existing proxy cube.
2. March through densityTexture.
3. Detect the first transition from below to above the iso-density.
4. Refine the crossing with approximately 5–8 bisection steps.
5. Compute the density gradient using central differences.
6. Negate and normalize that gradient to obtain the outward normal.
7. Transform the normal into world space.
8. Output or retain the reconstructed surface position and depth.
The gradient must account for non-cubic voxels:
float3 voxelSizeSimulation = fluidSize / densityResolution;
Otherwise your current 16 × 12 × 10 volume will produce stretched normals.
Use a ray step of roughly 0.5–1.0 voxel rather than the current fixed 0.4 simulation units. At the current 160 × 120 × 100 resolution, voxels are approximately 0.1 units wide, so a 0.4 step can completely skip thin fluid features.
The existing front-face culling is intentional: drawing the cube’s back faces guarantees proxy coverage when the camera is both outside and inside the volume. I would replace the TODO at [`main.cpp:156`](/home/tom/Documents/Ember/projects/fluidDynamics/src/main.cpp) with that explanation.
2. Add a refractive stage to the renderer
Your current ordering is deferred geometry → deferred lighting → one combined forward pass, as shown in [`vulkanRenderer.cpp:267`](/home/tom/Documents/Ember/engine/backends/vulkanRenderer/src/renderer/vulkanRenderer.cpp). That forward pass uses the same scene texture as its color attachment ([`vulkanForwardRenderPass.cpp:74`](/home/tom/Documents/Ember/engine/backends/vulkanRenderer/src/renderPasses/vulkanForwardRenderPass.cpp)).
Consequently, the fluid shader must not bind Renderer::GetRenderTexture() while simultaneously rendering into it. That would be an attachment feedback loop.
I would make the frame order explicit:
Deferred geometry
Deferred lighting
Forward opaque
Skybox
Copy/preserve opaque scene color
Fluid/refractive surfaces
Ordinary transparent objects
Post-processing
Avoid using a magic render-queue number for this. Add an explicit refractive render mode or stage and route those draw calls separately.
There are two good implementations:
- Minimal: copy the completed opaque scene into opaqueSceneColor, then render the fluid proxy cube while sampling that copy.
- More extensible: reconstruct into fluid surface buffers, then perform a fullscreen fluid composite.
For the extensible version, useful surface outputs are:
- fluidDepth: R32F
- fluidNormal: RGBA16F
- fluidThickness: R16F
- Optional exit position or refracted exit UV
This cleanly separates geometry reconstruction from optical shading and avoids scene-color feedback entirely.
3. Reflection and refraction
At the reconstructed front surface:
float3 incident = normalize(surfacePositionWorld - camera_position.xyz);
float3 reflectedDirection = reflect(incident, normalWorld);
float3 refractedDirection = refract(incident, normalWorld, 1.0f / indexOfRefraction);
For water, use:
IOR = 1.333
F0 = ((1 - IOR) / (1 + IOR))² ≈ 0.0204
Use Schlick Fresnel to mix reflected and transmitted light:
surfaceColor =
    fresnel × reflectedColor
  + (1 - fresnel) × transmittedColor
  + directSpecularLighting
Reflection sources, in recommended implementation order:
1. Skybox/environment cubemap.
2. Screen-space reflections against the opaque depth buffer.
3. Optional ray-traced or planar reflections later.
Raster rendering cannot follow a reflected ray into arbitrary off-screen scene geometry, so an environment cubemap plus SSR is the practical solution.
For refraction:
1. Refract the ray into the liquid.
2. March through the density field until it crosses the iso-surface again.
3. Refine that exit intersection.
4. Measure the internal travel distance.
5. Project the exit ray into screen space and sample opaqueSceneColor.
6. Reject or clamp samples that cross foreground opaque depth.
Initially, a normal-based screen-space UV offset is acceptable. The second density-field traversal gives substantially better thickness and silhouette behavior when you are ready for it.
4. Absorption and liquid color
Use Beer–Lambert attenuation along the internal fluid path:
float3 transmittance = exp(-absorptionColor * fluidDistance);
float3 transmittedColor =
    opaqueSceneColor.Sample(colorSamplerClampEdge, refractedUv).rgb
    * transmittance;
This should replace the current scalar-alpha approximation at [`volumeRaycast.frag.hlsl:111`](/home/tom/Documents/Ember/projects/fluidDynamics/shaders/src/volumeRaycast.frag.hlsl). A dedicated composite preserves RGB transmittance, which matters for realistic colored water.
Your existing opticalDepthTexture3d is oriented toward directional-light volumetric scattering. It is not required for basic surface refraction. Keep it for later light attenuation, subsurface scattering, or caustic generation.
5. Recommended implementation milestones
1. Surface debug shader
   - Iso-density hit only.
   - Display reconstructed normals.
   - Output correct SV_Depth.
   - Temporarily render opaque to validate silhouettes and occlusion.
2. Renderer refractive stage
   - Separate opaque/skybox from refractive/transparent work.
   - Preserve opaque color and expose opaque depth.
   - Add an explicit refractive render state.
3. Water MVP
   - Environment reflection.
   - Fresnel with IOR = 1.333.
   - Screen-space refraction.
   - Beer–Lambert absorption.
   - Direct specular lighting and shadow reception.
4. Higher-quality transmission
   - Trace the refracted ray through the density field to its exit.
   - Depth-aware screen-space lookup.
   - Total internal reflection.
5. Polish
   - SSR.
   - Foam from curvature/density variation.
   - Spray rendered with the old volumetric or particle path.
   - Temporal stabilization and empty-space skipping.
   - Caustics last.
I would not introduce marching cubes yet. Direct implicit-surface raycasting reuses your existing volume and is the shortest path to good water. Marching cubes becomes attractive later if you need the fluid to participate naturally in shadow rendering, hardware ray tracing, or conventional mesh-based tools.

- optional postOpaqueEffects

- postRenderCompute
The fluid remains a normal forward transparent material. It does not require a new MaterialPass.

    - other scene-color consumers

Present
The skybox does not need its own stage. It can remain ordered after opaque geometry through RenderQueue::skybox.
I would use these names:
Concept	Name
Opaque forward stage	RenderStage::forwardOpaque
Transparent forward stage	RenderStage::forwardTransparent
Optional screen-space work between them	RenderStage::postOpaqueEffects
Stable color exposed to transparent shaders	opaqueSceneColorTexture
Stable depth exposed to transparent shaders	sceneDepthTexture


“Post-opaque effects” is a useful injection point for SSR and other effects that require the completed opaque scene. Refraction itself is not such an effect: it is a transparent material consuming the result.
Do you need a new render stage and render pass?
For the forward split: yes, I would introduce two render stages and two logical render-pass contracts.
ForwardOpaqueRenderPass
It:
- Loads the color produced by deferred lighting.
- Loads the deferred depth.
- Draws opaque, wireframe, and skybox forward materials.
- Allows color and depth writes.
- Finishes with the scene color available for preservation/effects.
- Finishes with depth available for shader reads.
ForwardTransparentRenderPass
It:
- Loads the existing scene color.
- Loads scene depth.
- Allows color writes.
- Uses depth read-only.
- Draws transparent materials.
- Allows fragment shaders to sample opaqueSceneColorTexture and sceneDepthTexture.
The separate transparent render pass matters because its depth attachment can be declared read-only. Your current forward render pass uses VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL and combines depth-writing opaque materials with non-depth-writing transparent materials in one subpass ([`vulkanForwardRenderPass.cpp:100`](/home/tom/Documents/Ember/engine/backends/vulkanRenderer/src/renderPasses/vulkanForwardRenderPass.cpp)). That is not the right contract when transparent shaders also sample scene depth.
“Preserving” versus copying scene color
Semantically, call this preserving or capturing the opaque scene. But Vulkan still needs two image versions:
opaqueSceneColorTexture      immutable shader input
sceneColorTexture            current color attachment/output
A render-pass boundary only preserves the contents of one image. It does not allow the transparent shader to safely sample neighboring pixels from that image while simultaneously rendering into it.
Therefore one of these is required:
1. Copy the completed opaque color into another image.
2. Perform an out-of-place fullscreen composition from image A into image B.
3. Use an attachment-feedback extension, which I would not recommend as the core design.
For mesh-based refraction, an image copy is usually the cleanest option. The fact that the implementation uses vkCmdCopyImage does not mean “copy” needs to become a public rendering-stage concept.
Expose the semantic operation as something like:
PreserveOpaqueSceneColor(commandBuffer);
Internally, it performs:
sceneColor:
    COLOR_ATTACHMENT → TRANSFER_SRC

opaqueSceneColor:
    old layout → TRANSFER_DST

copy sceneColor → opaqueSceneColor

opaqueSceneColor:
    TRANSFER_DST → SHADER_READ_ONLY

sceneColor:
    TRANSFER_SRC → COLOR_ATTACHMENT
Your render textures already have transfer, sampled, and color-attachment usage, so the underlying resource type supports this ([`vulkanRenderTexture2d.cpp:34`](/home/tom/Documents/Ember/engine/backends/vulkanRenderer/src/gpuResources/textures/texture2d/vulkanRenderTexture2d.cpp)).
The existing secondary scene-color texture could technically be reused, because post-processing does not need it until after transparency. However, a dedicated opaqueSceneColorTexture gives the resource a stable meaning and avoids coupling transparency to post-processing ping-pong state. That is the cleaner first implementation.
Keep MaterialPass::forward
Do not add:
MaterialPass::fluid
MaterialPass::refraction
MaterialPass::screenSpace
Both forward stages execute forward-material shaders. Routing should depend on ForwardRenderMode:
opaque       → forwardOpaque
wireframe    → forwardOpaque
skybox       → forwardOpaque
transparent  → forwardTransparent
Thus both stage traits can share:
static constexpr emberCommon::MaterialPass materialPass =
    emberCommon::MaterialPass::forward;
Your existing ForwardRenderMode::transparent already provides the correct high-level classification and disables depth writes.
The fluid stays:
Material::CreateForward(
    emberCommon::ForwardRenderMode::transparent,
    ...);
It simply gains access to renderer-owned opaque scene inputs.
Renderer integration
The synchronization graph would become:
DeferredGeometry ─┐
Shadow ───────────┴→ DeferredLighting

                    ForwardOpaque

Concretely:
1. Replace RenderStage::forward with:
RenderStage::forwardOpaque
RenderStage::postOpaqueEffects
RenderStage::forwardTransparent
Only add postOpaqueEffects when you actually have an effect to schedule there.
2. Replace the current semaphore chain:

with:

You do not need new public draw APIs or new draw-call types.

About postOpaqueEffects
Do not create one giant screenSpaceEffects pass. Screen-space effects have different dependency points:
SSAO                  before deferred lighting
SSR                   after opaque rendering
Refraction            during transparent rendering
Bloom/tonemapping     after transparency
If you want extensibility, generalize the current post-processing mechanism into effect injection points:
enum class RenderEffectStage
{
    preLighting,
    postOpaque,
    postTransparency
};
Those queues can execute compute or fullscreen graphics work. A compute effect does not need a Vulkan RenderPass; a fullscreen graphics effect does.
For the initial fluid integration, however, postOpaqueEffects can remain empty. The necessary architectural change is simply:
forwardOpaque
preserve opaque scene color
forwardTransparent
That gives the renderer a generic foundation for water, glass, distortion, particles, and future SSR without introducing anything fluid-specific.

Vulkan Descriptor Pool System - Design Specification
Goals

Implement a scalable Vulkan descriptor allocation system supporting:

Static/Persistent descriptor pools
Long-lived descriptor sets
Dynamic pool growth
Optional individual descriptor freeing
Dynamic/Transient descriptor pools
Per-frame temporary descriptor sets
Fast allocation
Whole-pool reset
No individual freeing

System must:

scale automatically
avoid fragmentation where possible
support future bindless migration
minimize Vulkan allocation overhead
High-Level Architecture
DescriptorAllocatorPersistent
    ├── currentPool
    ├── usedPools
    └── freePools

DescriptorAllocatorFrame[FramesInFlight]
    ├── framePool
    └── vkResetDescriptorPool() every frame
1. Persistent Descriptor Allocator
Purpose

Used for descriptor sets with arbitrary or long lifetimes.

Examples:

material descriptor sets
texture bindings
static compute resources
renderer-global resources
editor/UI descriptors
Vulkan Pool Flags

Pools use:

VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT

to allow:

vkFreeDescriptorSets(...)
Behavior
Allocation
Allocate from currentPool
On exhaustion:
create new VkDescriptorPool
switch current pool
retry allocation
Freeing

Supports:

individual descriptor freeing
optional delayed destruction if needed
Pool Lifetime

Pools remain alive until:

renderer shutdown
allocator destruction
explicit pool garbage collection
Internal Structure
class DescriptorAllocatorPersistent
{
    VkDevice device;

    VkDescriptorPool currentPool;

    std::vector<VkDescriptorPool> usedPools;
    std::vector<VkDescriptorPool> freePools;

public:
    VkDescriptorSet Allocate(...);
    void Free(VkDescriptorSet set);
    void Reset();
};
Pool Exhaustion Handling

On allocation failure:

VK_ERROR_OUT_OF_POOL_MEMORY
VK_ERROR_FRAGMENTED_POOL

allocator:

grabs/reuses free pool OR creates new pool
retries allocation
Pool Sizing

Pools are intentionally large.

Example:

VkDescriptorPoolSize poolSizes[] =
{
    { VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,         1024 },
    { VK_DESCRIPTOR_TYPE_STORAGE_BUFFER,         1024 },
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER,2048 },
    { VK_DESCRIPTOR_TYPE_STORAGE_IMAGE,           256 },
};

maxSets = 4096;
2. Dynamic/Transient Descriptor Allocator
Purpose

Used for short-lived descriptor sets.

Examples:

per-frame descriptors
temporary compute descriptors
transient material instances
temporary render graph resources
Vulkan Pool Flags

Pools use:

flags = 0

NOT:

VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT

because:

individual freeing is unnecessary
reset model is faster
avoids fragmentation
Behavior
Allocation
allocate freely during frame
Reset

At beginning/end of frame:

vkResetDescriptorPool(...)

This invalidates all descriptor sets allocated from the pool.

Structure

One allocator per frame-in-flight:

DescriptorAllocatorFrame frames[FramesInFlight];

Each contains:

class DescriptorAllocatorFrame
{
    VkDescriptorPool pool;

public:
    void Reset();
    VkDescriptorSet Allocate(...);
};
Frame Lifecycle
Frame Begin
    -> reset descriptor pool

Rendering
    -> allocate transient descriptor sets

Frame End
    -> descriptor sets become obsolete automatically
Descriptor Pool Creation Strategy
CreatePool()

Allocator creates pools using configurable ratios.

Example:

struct PoolSizeRatio
{
    VkDescriptorType type;
    float ratio;
};

Example ratios:

{
    { VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER,          2.0f },
    { VK_DESCRIPTOR_TYPE_STORAGE_BUFFER,          2.0f },
    { VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER, 4.0f },
    { VK_DESCRIPTOR_TYPE_STORAGE_IMAGE,           1.0f },
}

Pool sizes derived from:

descriptorCount = ratio * maxSets;
Allocation API
Allocate()
VkDescriptorSet Allocate(
    VkDescriptorSetLayout layout);

Optional extension:

VkDescriptorSet Allocate(
    VkDescriptorSetLayout layout,
    void* pNext);
Pool Recycling
Persistent Allocator

Supports:

recycling unused pools
future defragmentation strategies

Optional:

move fully unused pools into freePools
Dynamic Allocator

No recycling needed.

Pool survives permanently and resets each frame.

Threading Considerations
Vulkan Requirement

Descriptor pool allocation is NOT thread-safe.

Recommended Strategy

Either:

mutex around allocation
OR:
one allocator per thread

Preferred future design:

ThreadLocalDescriptorAllocator

especially for transient descriptors.

Descriptor Set Layout Policy
Important

Descriptor set layouts should be:

cached
reused aggressively
immutable after creation

Avoid recreating layouts frequently.

Error Handling

Allocation must detect:

VK_ERROR_OUT_OF_POOL_MEMORY
VK_ERROR_FRAGMENTED_POOL

and recover automatically.

Any other error:

treated as fatal Vulkan error
Future Bindless Compatibility

System should remain compatible with future:

descriptor indexing
bindless textures
bindless buffers

Expected future direction:

fewer descriptor set allocations
large persistent descriptor arrays
descriptor updates instead of allocation churn

Current allocator design should therefore:

remain modular
not assume heavy descriptor allocation forever
Recommended Engine Usage
Persistent Allocator

Use for:

materials
textures
renderer-global descriptor sets
static compute resources
Dynamic Allocator

Use for:

per-frame descriptors
temporary GPU jobs
render graph transient resources
dynamic object bindings
Non-Goals

This system currently does NOT include:

descriptor set layout reflection cache
bindless implementation
descriptor update templates
descriptor buffer extension
multithreaded descriptor allocation
automatic pool shrinking

These may be added later.

Final Design Summary
Persistent Allocator
Feature	Supported
Dynamic pool growth	Yes
Individual descriptor free	Yes
Pool reset	Optional
Fragmentation possible	Yes
Long-lived descriptors	Yes
Dynamic Allocator
Feature	Supported
Dynamic pool growth	Optional
Individual descriptor free	No
Pool reset	Every frame
Fragmentation resistant	Yes
Long-lived descriptors	No

## 3. Replace dangling cross-material and default-material pointers

Problem:
Forward backend materials store their selected shadow material as a raw Material pointer. Deleting the shadow material leaves a dangling pointer. Default outline, shadow, and present materials are also stored as unprotected raw backend pointers and can be deleted through MaterialManager.

Goal:
All references between registered materials must remain safe when a target material is deleted or its slot is reused. Required default materials must not become dangling pointers.

Implementation plan:
1. Store cross-material relationships as generational MaterialIds at the core ownership layer rather than raw backend pointers where practical.
2. Resolve the selected shadow material when preparing a draw. If the handle is stale, use the default shadow material or disable the pass according to explicit policy.
3. If the backend must retain relationships, introduce a backend-safe handle/resolver or clear all reverse references before destruction. Do not retain an unchecked raw pointer.
4. Decide and document whether deleting an assigned shadow material automatically falls back to the default shadow material.
5. Protect required default materials. Either pin them until MaterialManager::Clear or replace/update the backend defaults atomically before allowing deletion.
6. Ensure cloned forward materials copy the safe shadow-material handle rather than a backend pointer.
7. Validate type/domain compatibility when assigning a stage override such as a shadow material.

Acceptance criteria:
- Deleting an assigned shadow material cannot cause a use-after-free.
- Reusing the deleted material slot cannot silently redirect an old relationship to an unrelated material.
- Default materials remain valid for the renderer's entire operational lifetime.
- Add tests for deletion, slot reuse, cloning, fallback behavior, and manager shutdown.

## 4. Couple call-descriptor pools to shader lifetime

Problem:
PoolManager stores CallDescriptorSetBindingPool objects in a map keyed by raw Shader pointers. DestroyMaterialShader and compute-shader destruction do not retire the corresponding pool. This leaves a dangling key and DescriptorSetBinding objects that still reference the destroyed Shader. Address reuse could cause a new shader to receive an old incompatible pool.

Goal:
A shader and every descriptor pool derived from its reflection/layout must have one coordinated lifetime.

Implementation plan:
1. Add an explicit PoolManager operation to retire the call-descriptor pool belonging to a shader.
2. Track checked-out bindings so retirement cannot delete a pool while handles are borrowed.
3. Decide whether retirement waits until all borrowed handles return or moves the entire pool into deferred garbage. Keep the operation frame-safe.
4. Invoke retirement from both material-shader and compute-shader destruction paths before the Shader and its descriptor-set layouts are destroyed.
5. Ensure deferred callbacks execute in this order: outstanding GPU use completes, descriptor bindings/pool are destroyed, and then shader layouts/pipeline layout are destroyed.
6. Prefer a stable shader ID as the pool key if the new MaterialShader handle work makes that available. Never allow allocator address reuse to identify an unrelated shader as the same pool owner.
7. Make returning a borrowed handle to a retired pool deterministic and safe; do not dereference a destroyed Shader while logging an error.

Acceptance criteria:
- No PoolManager entry survives its owning shader.
- A new shader can never receive descriptor bindings created from an old shader layout, even if memory addresses are reused.
- Shader deletion with checked-out bindings is either rejected or safely deferred.
- Material and compute shader paths follow the same lifetime rules.
- Add tests for pool creation, shader deletion, outstanding handles, address/slot reuse, and cleanup ordering.

## 5. Separate material domain from render stage and support multiple passes

Problem:
MaterialType currently represents forward, gizmo, outline, shadow, and present, which are mostly render stages. Although MaterialShader stores pipelines using a stage-aware key, every MaterialShader factory creates only one stage, every Material has one type, and stage-specific state and APIs are duplicated throughout the engine. A deferred surface material needs to participate in several passes without becoming several unrelated materials.

Goal:
Model a Unity-like shader/technique containing multiple passes. A Material remains one property instance and can participate in every render stage supported by its MaterialShader.

Implementation plan:
1. Replace or redefine MaterialType as a stage-independent MaterialDomain, for example surface, gizmo, postProcess, internal, or another deliberately chosen set.
2. Define a stable RenderStageId or MaterialPassTag used to select a pass such as depth, shadow, gBuffer, forwardOpaque, forwardTransparent, picking, or present.
3. Add a MaterialPass representation containing the shader stages, pipeline family, fixed render state, and supported variants for one pass tag.
4. Change MaterialShader to own a collection of MaterialPass objects rather than being created by one stage-specific factory.
5. Make the renderer query whether a MaterialShader supports a pass and obtain that pass's pipeline, rather than switching on the material's singular type.
6. Replace the separate optional render-state pointers in backend Material with a deliberate per-pass state/override representation. Avoid adding another pointer and another switch case for every new stage.
7. Define descriptor-layout rules across passes. Either require a compatible material descriptor-set schema for every pass in one MaterialShader or explicitly store per-pass bindings while presenting one coherent material-property API.
8. Route one submitted surface draw to the appropriate supported passes instead of requiring callers to construct unrelated materials for each stage.
9. Keep special internal passes such as present isolated where that produces a clearer API; not every renderer operation must be exposed as a user material.
10. Remove redundant one-to-one concepts such as separate RenderStage and PipelineType enums where a single typed pass identifier is sufficient.

Acceptance criteria:
- One surface Material can provide data to shadow/depth, G-buffer, and forward passes without duplicating user-managed material instances.
- Adding a raster pass does not require new Material subclasses and matching methods in every interface layer.
- Pass compatibility and missing-pass fallback behavior are explicit and testable.
- Existing forward, shadow, gizmo, outline, and present behavior still renders correctly.
- Add tests for multi-pass lookup, unsupported passes, descriptor compatibility, and per-pass render state.

## 6. Generalize raster pipeline descriptions before adding deferred rendering

Problem:
Current graphics pipeline classes hard-code render-pass selection and create variants from a small render-mode enum and vertex layout. Deferred rendering introduces multiple color attachments, attachment-specific blend/write state, additional formats, depth-only variants, and potentially different MSAA behavior. Adding more RenderMode enum values will not scale.

Goal:
Create raster pipelines from explicit, hashable pipeline descriptions so deferred passes use the same pipeline-cache mechanism without stage-specific duplication.

Implementation plan:
1. Define a RasterPipelineDescription containing all immutable state that affects pipeline creation: pass/render-target compatibility, topology, vertex layout, polygon/front-face state, depth/stencil state, multisampling, and one blend/write state per color attachment.
2. Separate dynamic state such as cull mode only when the required Vulkan feature is guaranteed and the state is intentionally material-mutable.
3. Replace renderModeIndex in PipelineKey with a stable hash or typed variant derived from the complete immutable pipeline description.
4. Move repeated Vulkan graphics-pipeline setup from ForwardPipeline, GizmoPipeline, OutlinePipeline, ShadowPipeline, and PresentPipeline into shared construction code.
5. Keep pass-specific policy in MaterialPass descriptions instead of separate nearly identical pipeline classes when no distinct behavior is needed.
6. Add support for the G-buffer attachment count, formats, write masks, and depth target.
7. Create pipelines lazily or deliberately prewarm selected variants; avoid eagerly creating every theoretical combination for every MaterialShader.

Acceptance criteria:
- The pipeline key includes every immutable state value that can make two Vulkan pipelines incompatible.
- Multiple render-target blend states are supported.
- Existing raster stages use the generalized creation path.
- A deferred G-buffer pass can be described without adding another large copy of the forward pipeline implementation.
- Add key equality/hash tests and pipeline-description tests independent of a live window when possible.

## 7. Add ray tracing as a separate pipeline family that shares material data

Problem:
The current PipelineKey assumes a raster pipeline selected by render stage, render mode, and vertex memory layout. Ray-tracing pipelines instead aggregate shader groups and use shader binding tables. DescriptorSetBinding also rejects descriptor types needed for acceleration structures.

Goal:
Allow ray tracing to reuse material properties and material identity without forcing ray-tracing pipelines into the raster MaterialShader::GetPipeline(stage, mesh) model.

Implementation plan:
1. Introduce an explicit pipeline-family distinction, at least raster, compute, and rayTracing.
2. Design ray-tracing pipeline ownership around shader groups and a shader binding table rather than one pipeline per material/mesh layout.
3. Define how a MaterialShader contributes closest-hit, any-hit, or intersection groups and how a Material instance selects its hit-group record.
4. Define per-material and per-instance data layouts for shader binding table records or descriptor buffers/sets.
5. Extend shader reflection and stage handling for ray-generation, miss, closest-hit, any-hit, intersection, and callable stages as required.
6. Add acceleration-structure descriptor support and any other required descriptor types to DescriptorSetBinding.
7. Add backend capability detection and fail clearly when ray tracing is unavailable.
8. Integrate the ray-tracing stage into renderer scheduling/resource transitions without treating its pipeline lookup as a raster PipelineKey variant.

Acceptance criteria:
- Raster pipeline lookup remains raster-specific and does not contain ray-tracing special cases.
- Multiple materials can select different hit groups within a shared ray-tracing pipeline/SBT.
- Material properties used by raster and ray passes have an explicit synchronization/layout contract.
- Acceleration-structure descriptors are reflected, allocated, updated, and lifetime-safe.
- Add reflection, shader-group indexing, SBT layout, descriptor, and unsupported-device tests.

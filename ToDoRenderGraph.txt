Dynamic Render Graph Migration
==============================

Purpose and status
------------------

This document transfers the context of the render-graph architecture discussion to a future Codex session.
It records the intended direction and migration sequence, not a finalized API or detailed implementation specification.
The migration has not been implemented as part of this discussion.


General goal
------------

Replace Ember's hard-coded render graph and fixed compute insertion points with a system that can compose arbitrary render and compute passes.
Adding a compute effect should require its pass, resource bindings, resource usage declarations, and any additional ordering constraints, without editing the central executor or adding another fixed compute slot.

Keep the existing graphics stages as reusable building blocks and preserve the current pipeline as the default composition.
Separate pass identity and scheduling from graphics pipeline/material classifications; these do not all need to become dynamic together.

Passes declare the resources they read and write.
The graph uses these declarations to establish dependencies and synchronization.
Explicit ordering constraints remain available where resource dependencies do not fully express the intended order.
Dependencies must support custom passes depending on other custom passes, including multiple predecessors and successors.

The initially proposed API accepted a compute shader, thread count, an earlier render stage, and a later render stage.
That captures useful placement constraints, but resource declarations are also necessary for correct synchronization.
The final public API remains undecided and should be designed when its requirements are concrete.

Start with a simple executor using the graphics queue for graph passes.
Automatic asynchronous scheduling, transient memory aliasing, automatic pass culling, and graph-plan caching are later improvements, not initial requirements.


Migration principles
--------------------

- Keep the renderer working throughout the migration.
- First make the existing structure data-driven while preserving its behavior; then migrate resource handling incrementally.
- Validate progress through actual rendering and Vulkan validation, not through a unit-test-driven migration plan.
- Correct-looking output alone does not establish synchronization correctness.
- Preserve rendering behavior, resource lifetimes, frames-in-flight handling, and application/editor integration.
- Transfer synchronization ownership one resource chain at a time. Do not leave competing transition systems responsible for the same boundary.
- Do not reorder passes freely until their dependencies and resource accesses are adequately described.
- Keep logical outputs distinct from physical resources, particularly for scene-color ping-pong and frames in flight.
- Resolve unclear design requirements with the user instead of treating suggestions in this document as finalized decisions.
- Follow AGENTS.md and implement proper architectural changes rather than accumulating workarounds.

ToDoTextureLayoutsAndRenderGraph.txt contains related, more detailed resource-state and texture-layout notes.
Use those notes where relevant, but do not make unrelated texture API changes a prerequisite for this migration.


Step-by-step migration
----------------------

1. Introduce pass instances and handles.
   Represent existing stages as registered pass instances executed through a general collection.
   Preserve today's execution order, resource handling, and synchronization.
   Keep runtime pass identity separate from existing graphics pipeline classifications.
   Checkpoint: baseline scenes look unchanged and a graph dump shows the existing execution order.

2. Represent dependencies as data.
   Replace manually named dependency connections with edges between pass handles.
   Establish a deterministic execution order that preserves existing order where dependencies allow it.
   Detect invalid references and cycles before submitting work.
   Preserve acquisition, presentation, and frame-completion behavior.
   Checkpoint: unchanged rendering and equivalent dependencies; invalid graphs produce clear diagnostics.

3. Separate recording from execution infrastructure.
   Make the executor responsible for providing recording resources and submitting work.
   Remove the requirement that recording resources are identified by a fixed render-stage enum.
   Migrate existing stages individually while preserving safe frame reuse.
   Checkpoint: unchanged rendering after each stage migration, including sustained rendering and resizing.
   Milestone: the existing renderer now executes through a general pass structure.

4. Introduce resource references and usage declarations.
   Let passes describe their image and buffer accesses, including whether existing contents must be preserved.
   Initially import existing resources without changing their allocation or ownership.
   Resolve references to the correct physical resources for the current frame.
   Collect declarations for inspection before using them to replace synchronization.
   Checkpoint: unchanged rendering and graph diagnostics that identify the intended resources and accesses.

5. Add resource-state tracking and synchronization planning.
   Plan synchronization from resource access history rather than stage names or image layouts alone.
   Cover image layout changes and read/write hazards for both images and buffers, including multiple readers before a later write.
   Keep proposed state separate from committed execution state so abandoned work cannot corrupt tracking.
   Initially inspect the plan without taking over existing synchronization.
   Checkpoint: existing rendering stays unchanged and planned dependencies can be inspected against a rendered frame.

6. Migrate the G-buffer producer/consumer chain.
   Make deferred geometry and deferred lighting declare their resource accesses and let the graph synchronize that chain.
   Align descriptor usage and render-pass boundaries with the graph's declared accesses.
   Remove the corresponding legacy transition and state bookkeeping as ownership transfers.
   Leave unrelated chains on their existing handling.
   Checkpoint: deferred rendering works on startup, after resizing, and across frame reuse without new validation errors.

7. Migrate the other rendering chains individually.
   Migrate shadows and lighting, outlines and their compute consumers, gizmos and their consumers, and forward rendering.
   Include resources accessed through meshes, materials, and descriptors.
   Preserve attachment contents where later rendering depends on earlier results.
   Checkpoint: exercise each migrated feature alongside earlier features, especially transparency and overlapping objects.

8. Move scene-color selection into graph preparation.
   Express scene-color effects through explicit inputs and outputs rather than named compute slots.
   Resolve ping-pong selection in scheduled order before preparing dependent bindings.
   Ensure forward rendering, later effects, presentation, and editor sampling use the intended result.
   Checkpoint: zero, one, two, and three effects all produce the correct final image in both the window and editor.

9. Migrate a visible buffer-compute chain.
    Choose compute work with a visible graphics result, such as vertex deformation or particle updates.
    Declare the compute output and its actual graphics consumption, then transfer synchronization responsibility to the graph.
    Keep internal dependencies explicit for multi-dispatch simulation sequences.
    Checkpoint: continuous animation and the fluid simulation remain correct without flickering, stale data, or new synchronization errors.

10. Complete external boundaries and lifetime handling.
    Cover uploads, resource updates, editor/GUI sampling, final outputs, readback where used, and resources shared with external compute work.
    Define the resource state and completion requirements at graph entry and exit.
    Preserve physical-resource state and submitted-work lifetimes across frames.
    Handle recreation and abandoned frames without invalid references, incorrect state advancement, or stalled frame completion.
    Checkpoint: resizing, minimize/restore, resource reloads, scene switches, and removing effects during rendering all work.

11. Expose arbitrary compute passes.
    Replace fixed compute-stage recording with general compute pass recording.
    Allow resource declarations and optional ordering constraints relative to built-in or custom passes.
    Temporarily translate existing compute entry points into graph passes to preserve callers during migration.
    Checkpoint: insert a visible diagnostic effect at several valid boundaries without modifying the executor.
    For example, compare a scene-color tint before and after transparent rendering and verify the expected difference.

12. Derive resource dependencies and support optional passes.
    Generate dependency edges from declared accesses and intended producers while retaining explicit ordering constraints.
    Define repeated-write and output-version semantics so consumers do not depend on guessed producers.
    Support enabling and omitting passes with explicit bypasses or alternative producers where necessary.
    Checkpoint: toggle effects and change custom pass chains while rendering; missing producers and conflicting constraints receive clear diagnostics.

13. Simplify execution on the graphics queue.
    Once resource declarations cover the relevant synchronization, remove redundant inter-pass submission synchronization.
    Use graph-generated barriers and group submissions where appropriate while preserving external boundaries and frame completion.
    Keep advanced queue scheduling out of this step.
    Checkpoint: rerun the baseline scenes, inspect a GPU capture, and compare timings with validation instrumentation disabled.

14. Remove the fixed compute architecture and document the result.
    Migrate remaining callers and remove the fixed compute slots, separate fixed-slot frame data, and obsolete execution plumbing.
    Remove remaining legacy synchronization only where the graph has taken responsibility.
    Update renderer documentation and reconcile overlapping migration notes.
    Checkpoint: the default project, editor, and fluid simulation work, including empty scenes, optional effects, resizing, and resource destruction.


Completion criteria
-------------------

- Built-in stages and custom passes share a general execution structure.
- Compute effects can be inserted at valid pass boundaries without adding fixed slots or executor branches.
- Resource declarations and explicit constraints establish the intended dependencies.
- The graph owns synchronization for graph-managed accesses, including their external boundary contracts.
- Scene-color outputs, frame reuse, resource recreation, and submitted-work lifetimes remain correct.
- Existing rendering features and application/editor behavior are preserved without new validation errors or unexplained performance regressions.
- Deferred optimizations remain separate follow-up work unless measurements justify them.
